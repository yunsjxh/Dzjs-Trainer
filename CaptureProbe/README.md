# CaptureProbe · 截屏探针

测「截屏替换到底通不通用」的靶程序。

## 为什么要有它

「挂上了钩子」和「真的能拦」是两回事。判据写松了会把目标进程自己的界面画花，
写紧了又漏拦。光有编译通过不算证据，得有一张图、一列像素摆在那里。

所以这个程序不去对照任何一份钩子清单。它只做一个动作：**用现实里真正存在的
抓屏写法去抓自己，然后看抓回来的像素是什么。** 哪条路被拦、哪条路绕过去了，
是结果，不是我预设的分类。

它同时干两件事：

- **当靶子**：窗口右边一块纯品红靶标，抓到的画面里该有它；底下还有一排四块
  视频靶，专治"单帧看不出问题、连续取帧才露馅"的情况；
- **当探针**：自己用 14 条抓屏路径去抓屏，把抓回来的像素判成真画面、贴了替换图、
  整幅纯白、整幅纯黑，还是被别的窗口挡住了。

静态判据一句话：**靶标在 = 这条路径没被拦；靶标没了 = 已经被换掉。**

## 视频靶：为什么静态靶标不够

一张截图被换掉，不代表连续取帧也被换掉。视频内容是另一码事 —— 同一段画面，
播放器可以走 GDI 直绘、走 D3D 交换链、走分层窗口，甚至让系统把它直接排除在
抓屏之外。能不能抓到，取决于「呈现方式 × 抓屏方式」这个矩阵。

窗口中间那排四块 160×90 的小画面就是给这个矩阵当靶子的，30fps 同步播放：

| 标记 | 呈现方式 | 现实里谁这样 |
|---|---|---|
| `G` | `SetDIBitsToDevice` 直绘 | MCI/DrawDib、老播放器、Swing/JavaFX |
| `D` | DXGI 翻转模型交换链 | PotPlayer、mpv、Electron、浏览器 |
| `L` | 分层窗口 `UpdateLayeredWindow` | overlay 那类实现，独立顶层窗 |
| `X` | `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` | 应用层自己申请"别抓我" |

画面里有一条竖贯全高的白色扫描条，位置由帧号唯一决定（七段数码管显示帧号）。
抓到一帧就知道它是第几帧；对不上，就说明这块内容压根没进这张截图。

每条抓屏路径跑完，结论区多一行：

```
视频 G✔ D✔ L✔ X✕ · 3/4 本帧
```

`✔` 本帧、`✕` 看不见（整块一个颜色）、`?` 有画面但不是这一帧、`-` 没覆盖到。

## 跑起来

```
CaptureProbe-x64.exe                   图形界面，F5 跑全部，Enter 跑选中
CaptureProbe-x64.exe --all             跑一遍就退，结果写进 probe-out\
CaptureProbe-x64.exe --all --keep-open 跑完留着窗口，方便对图
```

程序是 32 位和 64 位各一份，因为注入用的 DLL 也分两份，位数必须对上。

常用参数：

```
--out <目录>            改输出目录
--expect-image <图片>   给一张"替换图"，给了就能进一步确认"是不是这张图"
--topmost               窗口置顶
--no-target             调试用：不画品红靶标，把判定逼进 REPLACED 分支
```

也可以把这些写进同目录的 `CaptureProbe.ini`：

```ini
[Probe]
ExpectImage=replacement.png
TopMost=0
```

输出目录里每条路径一张 PNG，另外还有 `report.csv`（UTF-8 BOM，Excel 能直接开）
和 `summary.txt`（同样的内容，纯文本）。PNG 是原尺寸，方便逐像素复核。

## 14 条抓屏路径

| # | 名字 | 实际走的 API | 现实里谁这么干 |
|---|---|---|---|
| 01 | BitBlt 整屏 | `GetDC(NULL)` → `BitBlt(SRCCOPY)` | 最常见的桌面抓取 |
| 02 | BitBlt + CAPTUREBLT | 同上，带 `CAPTUREBLT` | 想连分层窗口一起抓的 |
| 03 | StretchBlt 整屏 | `GetDC(NULL)` → `StretchBlt(1:1)` | 老代码、缩略图缩放 |
| 04 | GetDIBits 全高 | `GetDIBits(hdcScreen, 32bpp)` | 抓完直接进 DIB 处理 |
| 05 | GetDIBits 上半屏 | 同上，只请求一半行 | 分块抓取、滚动截图 |
| 06 | GetDIBits 内存 DC | `GetDIBits(hdcMem, 24bpp)` | 对照组：跟屏幕无关 |
| 07 | GetDIBits 16bpp | `GetDIBits(hdcScreen, 16bpp)` | 老式远程/虚拟显卡 |
| 08 | GetWindowDC(桌面) | `GetDesktopWindow` → `GetWindowDC` | 另一种拿桌面 DC 的写法 |
| 09 | CreateDCW(DISPLAY) | `CreateDCW(L"DISPLAY")` | 直接开显示设备 |
| 10 | PrintWindow | `PrintWindow(hwnd, 0)` | 按窗口抓取、缩略图缓存 |
| 11 | PrintWindow FULL | 同上，`PW_RENDERFULLCONTENT` | Win8.1 之后的按窗口抓取 |
| 12 | DXGI 桌面复制 | `IDXGIOutputDuplication` | OBS、会议软件、浏览器共享 |
| 13 | 自检 · 内存 BitBlt | 内存 DC → 内存 DC | 不该被任何人动 |
| 14 | 自检 · 内存 Stretch | 内存 DC → 内存 DC | 同上 |

02 和 01 分开是因为有些工具会带 `CAPTUREBLT` 去抓分层窗口，行为和裸 `SRCCOPY`
不完全一样。06、13、14 是三条负样本 —— 没有它们，"全 PASS"可能只是有人把整台
机器都涂了。

## 结果怎么看

| 显示 | 含义 |
|---|---|
| `PASS · 靶标完整` | 抓到的就是真实屏幕 |
| `PASS · 有画面（位深不支持判靶）` | 16bpp 那条专用：靶色被色深量化吃掉了，但画面有结构，说明没被动 |
| `REPLACED · 命中替换图` | 和 `--expect-image` 给的图高度一致 |
| `REPLACED · 画面已被换掉` | 靶标没了，也不是纯色 —— 被换成了别的东西 |
| `SOLID · 整幅纯白` | 白底兜底 |
| `SOLID · 整幅纯黑` | 黑底兜底 |
| `BLOCKED · 靶窗被遮挡` | 靶窗不在最前，这次结果不算数 |
| `CLEAN` / `TOUCHED` | 自检项：内存 DC 有没有被改写 |

判定的技术细节：靶标 132×132 纯品红、中间挖一个黑十字，采样 8×8 个点
（用偶数网格是为了让采样点避开十字）。品红占比 ≥55% 判 PASS。
纯白/纯黑的判据是「整幅亮度极差 ≤6 且均值贴边」，一张很亮的正常画面不会被误判。

视频那四块另算：先看每块的平均亮度极差，一个颜色到底的（纯黑、纯白）判 `✕`
看不见；有结构就去找扫描条，条宽超过格子宽 1/8 的直接否定（整片白会让每一列
都像条），位置和帧号对得上才算 `✔`。

## 机器上跑出来的几件事

这些是实测结果，不是设计假设，换个环境可能变：

**整屏抓取看得见视频，按窗口抓取看不见一部分。** 01–09 全部 `G✔ D✔ L✔`：
DWM 合成之后，D3D 和分层窗口的内容都在桌面位图里。但 `PrintWindow(主窗)`
只画主窗自己的东西 —— `L` 是独立顶层窗，`X` 被系统排除，两块都是黑的。
这也是为什么录屏工具分"全屏模式"和"窗口模式"，效果真的不一样。

**`PrintWindow(hwnd, 0)` 抓不到 D3D 子窗口的内容。** 那条路径下 `D` 是 `?`
（有画面但对不上帧），加 `PW_RENDERFULLCONTENT` 才正常。要用 PrintWindow 抓
播放器窗口的，别省这个标志。

**`WDA_EXCLUDEFROMCAPTURE` 是硬边界。** `X` 那块对所有 GDI 路径都是 `✕`，
在抓回来的 PNG 里就是一块黑。`SetWindowDisplayAffinity` 只认顶层窗口，挂在
子窗口上直接失败 —— 我第一版就是这么写的，白忙一场。

**`GetDIBits` 的 `start` 从 DDB 存储起点算。** 源位图是 DDB，存储顺序
bottom-up，`start=0` 拿到的是屏幕**底部**的行。第 05 条只请求上半屏，正好能
看出映射对不对。

**虚拟显示器上 DXGI 抓不到帧。** ToDesk、向日葵、Parsec 那类虚拟屏，
`DuplicateOutput` 能成功但每帧全零。程序会把每个输出都试一遍，最后报
"所有输出都不可用"并附上每条的原因 —— 这是环境限制，不是谁拦的。

**16bpp 的 `BI_RGB` 可能是 555 不是 565。** 这台机器就是 555，按 565 解整幅偏绿。
程序看 bit15 有没有被用过自动判别。

## 已知限制

**第 10/11 条会暴露一个覆盖面问题。** 如果替换开着、又不检查 `hwnd`，
靶程序抓**自己**的窗口也会被换成替换图 —— 对"抓屏软件"是对的，对"程序内部用
PrintWindow 做缩略图缓存"就是误伤。真机上看到这条从 PASS 变 REPLACED，
先想清楚是哪种场景。

**视频靶是程序自己画的，不是解码器。** 它验证的是"呈现路径能不能被抓到"，
不验证 H.264 硬解、DXVA 表面、MPO 这些东西 —— 那些要真播放器才能压出来。

**只测主屏/虚拟屏整块。** 多显示器时从虚拟屏左上角开始抓，副屏在左边
（负坐标）也支持，但没有单独的"只抓某一块屏"的选项。

**注入之后窗口操作可能变慢。** 如果靶程序自己被注入，`SetWindowPos`、
`ShowWindow` 这些会过一遍 detour。抢前台那几步可能不灵，结果里出现 BLOCKED
就是提示。

## 构建

不进 sln，直接 cl.exe：

```sh
sh build.sh          # x86 + x64
sh build.sh x64      # 只编一个
```

产物在 `../Release/captureprobe-x86/` 和 `../Release/captureprobe-x64/`。
依赖只有 Win32 + GDI + D3D11 + DXGI + WIC，没有第三方库。
